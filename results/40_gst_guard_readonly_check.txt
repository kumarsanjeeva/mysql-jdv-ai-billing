## 6. Answer
- Does ANY guard verify that the sum of order_items.gst_value equals the order's gst_value?  NO. The only guard that touches these columns is GUARD 3, and it checks only
  orders.total = orders.subtotal - orders.discount_value + orders.gst_value (tolerance 0.01) using values stored on the ORDER row. No trigger, CHECK constraint or view
  rule in sql/ or in the restored database compares order_items.gst_value (or price * qty) with the order's gst_value or subtotal.
- Was order 77 of v2 run 1 (order gst_value 72.00, subtotal 1440.00, total 1512.00; items 43 and 44 with gst_value 0.00 because the model did not send it and the column default is 0)
  therefore accepted by design?  It was accepted because it satisfies every check that exists: GUARD 3 holds (1512.00 = 1440.00 - 0.00 + 72.00), GUARD 6 holds
  (item prices equal catalog prices 900.00 and 90.00, after the model's third attempt supplied product ids), GUARD 4 and GUARD 8 hold (business 1 throughout).
  No rule exists that would have rejected item-level GST of 0.00 against an order-level GST of 72.00, so under the current rule set the write is permitted.
  (Whether that is the INTENDED design is not stated anywhere in the files I read; this document states only what the rules do.)
